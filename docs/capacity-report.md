# Capacity report

Generated by `cmd/loadgen`, which exits non-zero when a target is missed, so a
capacity claim fails a pipeline rather than producing a document nobody reads.

```
go run ./cmd/loadgen \
  --publish-url http://gateway:8080/publish \
  --tenant <id> --app-key <key> --secret <secret> \
  --connections 100000 --publish-qps 1000 \
  --duration 60s --report capacity.json
```

## Documented targets

| Target | Value | Source |
|---|---|---|
| Connections per instance | 100,000 | proposal |
| Platform publish rate | 1,000 msg/s | proposal |
| Per-viewer bandwidth budget | 2 KB/s | proposal |
| Single-instance egress | 1.6 Gbps | derived |
| Publish-to-delivery p50 | < 50 ms | proposal |
| Publish-to-delivery p95 | < 100 ms | proposal |
| Publish-to-delivery p99 | < 200 ms | proposal |
| Publish acceptance rate | ≥ 99% | derived |
| Message size | 200 B average, 4 KB max | proposal |

**Acceptance below 100% is expected and is not a failure by itself.** The discard
policy deliberately refuses publishes without telling the publisher, which lowers
the acceptance rate by design. What matters is that the *refusal* is attributed:
the outcome breakdown separates `accepted` and `degraded` from each refusal
code, so a rate limit working as configured is distinguishable from a capacity
problem.

## End-to-end, against a serving instance

The sections below measure components in isolation. This one drives the real
gateway over HTTP and WebSocket with `cmd/loadgen`, which holds a subscriber
population, publishes into it, and reports what the instance actually pushed.

```
go run ./cmd/loadgen \
  --publish-url http://127.0.0.1:8080/publish \
  --tenant t1 --app-key <key> --secret <secret> \
  --connections 1000 --publish-qps 10 \
  --duration 30s --ramp 5s --report c1000.json
```

**The publish rate here is 10 msg/s, not 1,000.** At 200 B average that is
2 KB/s per viewer, which is exactly the documented per-viewer budget — so this
configuration spends the whole bandwidth allowance on every one of its
subscribers. 1,000 msg/s is the *platform* target and is only reachable by
spreading it over channels; sending it to one channel would ask every viewer to
take 200 KB/s, which is a hundred times the budget.

| Connections | Per viewer | Total egress | Delivery p50 | p95 | p99 | Publish p99 | Conforms |
|---:|---:|---:|---:|---:|---:|---:|:--:|
| 1,000 | 2,004 B/s | 2.00 MB/s | 26.0 ms | 27.8 ms | 30.8 ms | 4.4 ms | **yes** |
| 5,000 | 1,795 B/s | 8.97 MB/s | 37.7 ms | 106.8 ms | 137.6 ms | 104.4 ms | no |
| 10,000 | 734 B/s | 7.34 MB/s | 26.6 ms | 77.0 ms | 115.3 ms | 88.6 ms | no |

30 s per run, 8 probe connections, one freshly started gateway per configuration.
Budgets are p50 < 50 ms, p95 < 100 ms, p99 < 200 ms.

### The per-viewer budget is the thing that held

At 1,000 connections the instance pushed **2,004 B/s per viewer** against a
documented 2,000 B/s budget. That is the capacity model confirming itself: the
bandwidth bound binds before the connection count does, and instance count falls
out of dividing available egress by that per-viewer rate.

The 10,000-connection row delivered *less* per viewer than the 5,000-connection
row, which looks like a regression and is not one. A fixed 10 msg/s spread across
more subscribers gives each viewer fewer messages per second, and the run is
shorter than the ramp at that size — the connection population is still growing
while the measurement window is already closing, so per-viewer rate is diluted
rather than throttled. Total egress also falls between the two runs. Both are
artifacts of holding a 10,000-connection population on one 8-core box, and neither
is a claim about the deployed shape.

### Nothing was dropped, and that is a real result

Across all three runs: **zero dial failures, zero gap notices, every admitted
message delivered.** No subscriber was ever told it fell behind. The failures
above are all latency, and latency is the budget that is genuinely tight — which
is the opposite of the failure mode a fanout path usually degrades into.

### What this machine cannot measure

This box tops out well below the documented targets, for reasons that belong to
the measurement setup rather than the service:

- **~16,384 usable client ports.** macOS allocates ephemeral ports from
  49152–65535. Opening 50,000 sockets from one IP to one destination exhausts the
  range; the OS refuses to assign ports and the gateway never sees the attempt.
  This is a client-side limit and the 19,540 "dial failures" in that run are the
  OS, not the service.
- **The gateway runs under `GOMEMLIMIT=4GiB` beside the load generator** on the
  same 16 GB of RAM. Running configurations back to back killed the gateway
  mid-run and turned two earlier results into noise. Every number in the table
  above comes from a freshly started gateway, which is why that restart is in the
  measurement script rather than being done by hand.
- **The load generator and the service share 8 cores.** They contend, so the
  latency figures above are pessimistic relative to a deployment where the
  generator is off-box.

So **100,000 connections and a sustained 1,000 msg/s remain unverified** — not
failed, untested. Reaching them needs ephemeral ports widened, the generator off
the service's host, and several instances.

## Measured on this machine

Numbers below are from `go test -bench` on a single developer machine
(Intel i5-1038NG7, 8 cores), which is **not** the deployment target. They are
recorded to show the shape of the result, not to certify capacity.

### Fanout path

| Configuration | Bytes/s | Packets/s | Allocations/op |
|---|---:|---:|---:|
| 1,000 conns, merge 1 | 881 MB/s | 4,033 | 6 |
| 1,000 conns, merge 20 | 909 MB/s | 4,158 | 6 |
| 10,000 conns, merge 20 | 569 MB/s | 260 | 14 |

Two things this table is evidence for:

- **Allocations do not scale with subscriber count.** 6 at a thousand connections
  and 14 at ten thousand is sublinear. That sublinearity *is* the serialize-once
  property holding: the work per message is one encode plus a memcpy per
  subscriber, and none of it re-encodes.
- **Byte rate barely moves between merge 1 and merge 20** (881 vs 909 MB/s) while
  packet count would collapse. That is the coalescing-is-a-latency-dial claim
  confirmed at the whole-pipeline level: merging cuts packets, not bytes.

### Store traversal

| Shape | Per traversal |
|---|---:|
| Contiguous slice floor | 979 ns |
| Subscription store | 1,000 ns |
| Hash map (rejected shape) | 183,793 ns |

The store sits at 1.02× the slice floor and 188× away from the map. That
comparison is asserted as a test, not merely recorded here, so a regression to a
map fails the build.

### Flush cost against idle population

| Idle connections | Per flush pass |
|---:|---:|
| 1,000 | 16.2 µs |
| 100,000 | 16.5 µs |

A 100× increase in idle connections costs 1.02× more per pass. This is what
lets a large idle population be free, and it is asserted as a test.

### Degradation ladder span

| Level | Packets per 5,000 offered | Admitted | Merge target |
|---|---:|---:|---:|
| normal | 250 | 100% | 20 |
| reduced | 47 | 76% | 80 |
| sampled | 12 | 50% | 200 |
| critical | 0 | 0% | 400 |

**Span L0 to L2: 20.8×**, stated against offered content rather than admitted
content so the levels are directly comparable. L3 sheds ordinary content
outright, so a ratio against it would measure that the content is gone, not that
the instance got faster.

## Compression (`permessage-deflate`)

Measured by `internal/protocol/compress_test.go`, which asserts the thresholds
rather than only recording them.

| Batch size | Deflated / raw |
|---:|---:|
| 1 | **1.123** |
| 5 | 0.308 |
| 20 | **0.120** |
| 50 | 0.072 |

**A single unmerged message compresses to 112% of its original size.** Deflate
framing costs more than a 200-byte payload saves. A coalesced batch of twenty
saves **88%** — 1,316 bytes to 158.

### Conclusion

**Compress large batches, never small ones.**

The CPU is close to free when the bandwidth bound binds, and an 88% reduction on
the path that carries almost all traffic would move the platform from 1.6 Gbps to
roughly 200 MB/s per instance — a materially different capacity position.

### Why the decision is per batch, not a setting

The first framing of this was "enable compression only where coalescing is on".
That is wrong, and testing it showed why.

`MergeRatio` is a **target, not a guarantee**. A coalescing window closes on
elapsed time as well as on reaching the merge target, so a lightly loaded channel
emits one-message batches even at `MergeRatio=20` — verified by
`TestMergeRatioIsATargetNotAGuarantee`. A config-level check against
`MergeRatio` would therefore have passed while still compressing exactly the
batches that expand.

The decision is made per batch on its real size, in `protocol.ShouldCompress`,
with a threshold of 4: a batch of one expands to 112%, a batch of five already
reaches 31%, and the full merge target of twenty reaches 12%. A threshold below
two is refused at startup, because a per-batch expansion is invisible until
someone reads an egress meter.

So the rule that holds is narrower and more useful than "coalescing on means
compress": **compress a batch only when it actually contains enough messages to
pay for the framing.**

| Multi-instance at target connection count | **Not verified** |
| Broadcast topology at production scale | **Not verified** |
| Single-instance connection ceiling | **Not verified** — measured to 10,000; the 16k client-port ceiling on this box bounds the test, not the service |
| Sustained target publish rate | **Not verified** — measured at 10 msg/s, the rate the per-viewer budget allows on one channel |
| Latency percentiles under target load | **Partially verified** — in budget at 1,000 connections, over at 5,000 and 10,000 |
| Per-viewer bandwidth budget | **Verified at 1,000 connections** — 2,004 B/s against a 2,000 B/s budget |

### What is deliberately not claimed

MVP-scale evidence does not validate the multi-instance delivery path. At the
documented connection target the platform runs on one or two instances, and the
multi-instance tests use small connection counts because a large-scale
multi-instance run is a load test, not a unit test.

The broadcast topology is built correct rather than simplified, and the
exactly-once property is asserted directly across instance counts, but **that is
correctness evidence, not capacity evidence.** Whether it holds at 100,000
connections across several instances with real network links between them is
unmeasured, and the honest statement is that the architecture is ready for that
test rather than that it has passed it.

The four unverified rows above are what a load test against the deployment target
would close. Until then, the capacity model in `design.md` is derived from the
measured bandwidth and packet figures above, and every absolute capacity claim in
it remains a projection.
## Build

The image builds from the vendored module tree and needs no network access:

```
docker build -t push .
```

Verified on Docker 29.8.2 against the default distroless base: the image builds,
both binaries run as uid 65532, `/readyz` and `/livez` return 200, `SIGTERM` exits
0, and no secret appears in the image or its history. The image is 23.7 MB and
has no shell, confirmed by `/bin/sh` being absent rather than merely unused.

Two constraints were found while verifying this, both worth keeping:

- **The Go module proxy must be reachable, and `proxy.golang.org` often is
  not.** It times out from most networks outside Google's own. The build sets
  `GOPROXY=https://goproxy.cn,direct`, overridable with `--build-arg`, and the
  module tree is vendored so the default path needs no network at all. Both were
  tested: the same `go mod download` finishes in about six seconds through
  goproxy.cn and fails on a handshake timeout through the default.
- **`gcr.io` is intermittent.** The distroless base resolved on some attempts
  and timed out on others. It is the correct base and the build should keep
  failing loudly rather than silently fall back to something with a shell in it;
  `--build-arg RUNTIME_BASE=alpine:3.22` exists for verification where gcr.io
  cannot be reached.
- **`USER` must be numeric.** `USER nonroot:nonroot` is a distroless-specific
  name; the image fails to start with `unable to find user nonroot` on any base
  without that passwd entry. `65532` is the uid `distroless:nonroot` uses, and a
  numeric `USER` needs no lookup.

Note that `gofmt -l .` now also lists files under `vendor/`, which are third-party
and excluded from `./...` by the go tool. Format checks should run against
`./cmd ./internal`.

## Gateway wiring

The gateway serves three listeners and the data plane is wired end to end:

| Port | Surface | State |
|---|---|---|
| `:8080` | `/publish` (HTTP), `/sub` (WebSocket) | wired |
| `:8081` | `/admin/*` | wired |
| `:8082` | `/readyz`, `/livez`, `/metrics` | wired |

Verified end to end in the container: an administrative bootstrap creates the
first principal, the admin API issues an application credential, a subscriber
completes the `hello` handshake and subscribes, a publish is admitted, and the
message is delivered over the socket as a `message` frame.

### Message identifiers travel as strings

Identifiers use 63 bits (41 ms, 10 instance, 12 sequence). A JavaScript number
holds 53 bits exactly, so emitting an id as a JSON number silently rounds every
value above 2^53 and two distinct messages would reach a client looking
identical. The gateway emits a decimal string and the SDK parses it into a
`bigint`. Changing this later would be a breaking change to the wire format, so it
is asserted by a test rather than left implicit.

### The first administrator is seeded from configuration

The admin API authorizes a caller against a stored grant, so an instance with no
grant has no reachable administrator and cannot be unlocked through its own API —
a lockout, not a security property. `BOOTSTRAP_TENANT` and `BOOTSTRAP_SUBJECT`
seed one principal from configuration at start-up, both required together, and
`BOOTSTRAP_ROLE` is checked at load so a typo cannot leave an instance that looks
configured and authorizes nobody.

This is deliberately not an endpoint. An endpoint that can mint an
administrator is an unauthenticated privilege escalation, and the fact that it
only works once is a property of timing rather than of access control.

### Administrative writes refresh the config cache

A single-instance deployment receives no change notification, so the config cache
is refreshed directly after each administrative write. Without it the admin API
and the data plane disagree: a credential created through the API is durable in
the database but absent from the cache, so every publish and subscribe using it is
refused as an unknown credential while the operator looks at a successful
creation.

## Still unverified

The items in **Conformance** above remain open. The load generator has now been
run end to end against a serving instance at up to 10,000 real WebSocket
subscribers, which verifies the per-viewer bandwidth budget and the
no-content-dropped property, and bounds delivery latency short of the documented
percentiles.

What this work did **not** establish is the 100,000 connection ceiling or the
sustained 1,000 msg/s platform publish rate. Both are untested rather than failed:
this machine's ephemeral port range caps a single-source subscriber population at
about 16k regardless of what the service can hold. Closing them needs the
generator on a separate host, a widened port range, and more than one instance.

Two measurement defects were found and fixed while gathering this data, both of
which had been producing numbers that looked better than reality:

- Only the first subscriber to see a message was counted, so deliveries and bytes
  were flat across 1,000 and 10,000 connections. Connections are now split into
  probes that sample latency and load connections that carry the fanout.
- The percentile helper read an unsorted sample, which could place p50 above p95,
  and a run whose probes matched nothing read every percentile as 0.0 and passed.
  Both are now covered by tests that fail without the fix.
